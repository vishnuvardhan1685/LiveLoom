## 1. PROJECT OVERVIEW

LiveLoom is a **real-time collaborative code editor** that runs in the browser — think Google Docs, but for writing code. Multiple users can open the same "room" and type in the same files at the same time, with every keystroke instantly synced to all other connected users.

**What problem it solves:** Developers or students who want to pair-program, review code together, or teach live without needing to share screens or copy-paste snippets.

**Target users:** Developers, coding bootcamp students, technical interviewers, and teams who want a lightweight self-hosted or cloud-hosted live coding workspace.

### Journey 1 — Signup and Login

1. User fills the form in `SignupPage.jsx` / `LoginPage.jsx`.
2. `useAuth.js` calls `authApi.signup()` or `authApi.login()` → `POST /auth/signup` or `POST /auth/login`.
3. `auth.controller.js` hashes the password with `bcrypt` (10 rounds), saves to `User` model, signs a JWT (`signJwt` in `utils/jwt.js`).
4. Response: `{ token, user: { id, email, name } }`.
5. `useAuth.js` → `persist()` stores token as `ll_token` and user as `ll_user` in `localStorage`.
6. `api.js` Axios interceptor automatically attaches `Authorization: Bearer <token>` to every future request.

### Journey 2 — Creating and Entering a Room

1. Dashboard: user types a name, clicks Create → `POST /rooms` → `rooms.controller.js` → `createRoom()`.
2. Room is created in MongoDB with `members: [{ userId, role: 'owner' }]`.
3. Response includes the new room ID; `navigate(/room/:id)` is called.
4. `EditorPage.jsx` loads, calls `GET /rooms/:id` to get room metadata and the caller's role.
5. `useWsTicket.js` calls `POST /rooms/:id/tickets` → `issueWsTicket()` → `ticket.service.js` → `issueTicket()`.
6. `useYjsDoc.js` creates a `Y.Doc`, attaches `IndexeddbPersistence`, creates `WebsocketProvider` with `?ticket=&roomId=` params.
7. `y-websocket` opens a WebSocket to the server.

### Journey 3 — Real-Time Document Sync

```
User types in Monaco editor
      |
MonacoBinding (y-monaco) -> Y.Text mutation
      |
Y.Doc fires 'update' event with binary delta
      |
docSync.js ensureUpdateBroadcast listener
      |
  broadcastLocal()         publishDocUpdate()
  (other local WS clients) (Redis channel room:<id>:doc)
                                |
                     Other server instances
                     receive via redisBridge subscriber
                                |
                      applyRemoteDocUpdate() -> Y.applyUpdate()
                                |
                      doc 'update' fires -> broadcastLocal()
                      (REMOTE_ORIGIN guard: does NOT publish back to Redis)
```

### Journey 4 — Joining via Invite

1. Owner opens `InviteModal.jsx`, chooses role + expiry + max uses → `POST /rooms/:id/invites`.
2. Response includes `token` (random 32-char hex) and `/join/:token` link.
3. New user pastes token or link in Dashboard.
4. `invitesApi.redeem(token)` → `GET /invites/:token` → `invites.controller.js` → `redeemInvite()`.
5. Server checks expiry, then atomically increments `usesSoFar` with a `$expr`-guarded `findOneAndUpdate`.
6. User is added to `room.members`. Response: `{ roomId, role }`.
7. `navigate(/room/:roomId)` — user enters the editor.

## 6. AUTHENTICATION & SECURITY

### How auth works

- **JWTs** — Issued on signup/login by `signJwt()` in `utils/jwt.js`. Signed with `JWT_SECRET`. Payload: `{ sub: userId, email, name }`.
- **Token storage** — Stored in `localStorage` as `ll_token`. **Not in an httpOnly cookie**, so JavaScript can read it (see Weaknesses).
- **Route protection (HTTP)** — `middleware/auth.js` → `requireAuth()` reads `Authorization: Bearer <token>`, verifies with `verifyJwt()`.
- **Route protection (WS)** — Uses a separate short-lived HMAC ticket (not the JWT). `connection.js` calls `consumeTicket(ticket)` synchronously.
- **Room role protection** — `middleware/requireroomrole.js` loads the room from MongoDB and checks `room.getRole(req.user.id)`.
- **Frontend route guards** — `RequireAuth` and `RequireGuest` in `router.jsx`.

### Password handling

- Hashed with `bcrypt` at `SALT_ROUNDS = 10` in `auth.controller.js`.
- Comparison uses `bcrypt.compare()` — constant-time.
- Minimum length of 8 characters enforced server-side.
- Never returned or logged.

### CORS

- Configured in `app.js` with the `cors` package.
- Allowed origins come from `CLIENT_ORIGINS` env var, parsed in `config/env.js`.
- Supports wildcard patterns like `https://*.vercel.app`.

### Rate limiting

- **Global limiter**: in-memory sliding-window in `middleware/security.js` → `createRateLimiter()`. Default 10,000 req/min per IP.
- **Auth limiter**: 1,000 req / 15 min per IP on `/auth/*` routes.
- **Ticket limiter**: 2,000 req / 1 min per IP on `/rooms/:id/ws-ticket`.
- **WS per-socket limiter**: 300 messages/sec per socket in `ws/connection.js`. Excess → close code 1008.

### Input validation & injection prevention

- `middleware/security.js` → `sanitizeInputs()` strips object-type values from `req.body` to prevent MongoDB NoSQL injection.
- `express.json({ limit: '5mb' })` caps HTTP body size.
- `helmet` adds security headers.

### Security gaps

- JWT stored in `localStorage` — vulnerable to XSS.
- CSP is disabled in `helmet` config (`contentSecurityPolicy: false` in `app.js` line 22).
- In-memory rate limiter resets on restart; not shared across instances.
- No email verification on signup.
- `ForgotPasswordPage` has no backend.
- Password has no complexity requirement (only minimum length).

### SSE Events (GET /rooms/events)

| Event type | Who receives it | Payload |
|---|---|---|
| `room-deleted` | All members of the deleted room | `{ type, roomId, roomName }` |
| `role-changed` | The user whose role was changed | `{ type, roomId, roomName, role }` |
| `role-changed-ack` | The owner who made the change | `{ type, roomId, roomName, targetName, targetUserId, role }` |

### WebSocket Protocol (`ws://…/ws?roomId=&ticket=`)

All messages are binary (Uint8Array). Uses the Yjs sync protocol framing.

| Message type | Direction | What it does |
|---|---|---|
| Sync Step 1 (byte 0,0) | Client → Server | Client sends state vector; server responds with missing updates |
| Sync Step 2 (byte 0,1) | Server → Client | Server sends all updates the client is missing |
| Update (byte 0,2) | Bidirectional | Incremental document update (a single edit) |
| Awareness (byte 1) | Bidirectional | Cursor position, user name/color, typing status, active/inactive |

**Custom WS close codes:**

| Code | Meaning |
|---|---|
| 4001 | Invalid or expired ticket |
| 4002 | Room is full (over maxUsers) |
| 4403 | Room was deleted — stop reconnecting |
| 1008 | Per-socket rate limit exceeded (>300 msg/sec) |
| 1009 | Frame exceeds 5.2 MB maxPayload limit |

## 9. REAL-TIME / CORE LOGIC

### Yjs CRDT Document Sync

**What is a CRDT?** A data structure that two people can edit independently and their edits will always merge correctly. Yjs is a CRDT library.

**Step 1 — New client connects**
(`ws/connection.js` → `handleConnection()`)
1. `consumeTicket(ticket)` — HMAC verify + expiry check.
2. Attaches a message queue BEFORE any `await` to avoid dropping early frames.
3. `await roomState.loadRoleMap(roomId)` — loads roles from MongoDB (cached).
4. `await roomState.incrementActiveCount(roomId)` — INCR in Redis; rejects if > maxUsers.
5. `await docRegistry.getOrCreateDoc(roomId)` — returns in-memory Y.Doc or loads snapshot from MongoDB.
6. `docSync.sendSyncStep1(ws, doc)` — sends the server's state vector to the client.
7. Flushes the message queue — any frames that arrived during setup are processed now.

**Step 2 — Client sends its state vector (Sync Step 1)**
`docSync.js` → `handleSyncMessage()` → builds a Sync Step 2 reply containing every update the client is missing → sends it back.

**Step 3 — User types something**
Monaco → `y-monaco` → `Y.Text.insert()` → Y.Doc fires `'update'` event.

`docSync.js` → `ensureUpdateBroadcast()` listener:
- `roomSockets.broadcastLocal()` — sends to every other WS on THIS server instance.
- `redisBridge.publishDocUpdate()` — publishes binary delta to Redis channel `room:<id>:doc`.
- `snapshotService.scheduleSnapshot()` — debounces a MongoDB save.

**Step 4 — Other server instances receive the update**
`redisBridge.js` → `subscriber.on('messageBuffer')` → `applyRemoteDocUpdate()` → `Y.applyUpdate(doc, uint8, REMOTE_ORIGIN)`.
The Y.Doc fires `'update'` again with `REMOTE_ORIGIN` as origin.
The `ensureUpdateBroadcast` listener sees `origin === REMOTE_ORIGIN` → skips `publishDocUpdate` (no loop!) → calls `broadcastLocal`.

**Step 5 — Snapshot persistence**
`snapshot.service.js` → `scheduleSnapshot()`:
- Waits 3 seconds of inactivity OR 50 accumulated updates — whichever comes first.
- `flush()` → `Y.encodeStateAsUpdate(doc)` → `DocumentModel.findOneAndUpdate(..., { upsert: true })` → saves to MongoDB.

### Awareness (Cursors)
Same pipeline but on `room:<id>:awareness` channel.
`awareness.js` tracks which Awareness client IDs each WebSocket owns.
On disconnect: `clearConnAwareness()` → cursor disappears for everyone.

### Invite Race Condition Protection
(`invites.controller.js` → `redeemInvite()`)
```js
Invite.findOneAndUpdate(
  { _id, expiresAt: { $gt: now }, $expr: { $lt: ['$usesSoFar', '$maxUses'] } },
  { $inc: { usesSoFar: 1 } }
)
```
If two users hit the last slot simultaneously, only one wins because MongoDB processes the conditional update atomically.

### WS Ticket Design
(`services/ticket.service.js`)
- Format: `base64url(header).base64url(payload).base64url(HMAC-SHA256-signature)`.
- TTL: 10 minutes. Reusable (not single-use) so y-websocket auto-reconnect and React StrictMode double-mounts don't cause 4001 errors.
- Role is NOT embedded in the ticket — always looked up live from the in-memory role map.

## 12. STRENGTHS

1. **Correct CRDT implementation** — Yjs is properly wired end-to-end: `y-indexeddb` for offline cache, `y-websocket` for transport, `y-monaco` for editor binding, server Y.Doc with snapshot persistence and eviction. The `REMOTE_ORIGIN` sentinel prevents Redis update loops.

2. **Stateless reusable WS tickets** — HMAC-signed tickets handle `y-websocket` auto-reconnect and React StrictMode double-mounts without 4001 errors. The design is clearly documented in `ticket.service.js` comments.

3. **Atomic invite redemption** — The `$expr`-guarded `findOneAndUpdate` in `invites.controller.js` correctly prevents race conditions when two users redeem the last invite slot simultaneously.

4. **Graceful shutdown** — `index.js` handles `SIGTERM`/`SIGINT` with a 5-step sequence: stop accepting connections → close WS clients → flush Yjs snapshots → close Redis → close MongoDB. No data loss on deploy.

5. **Early message queue in WS connection** — `connection.js` attaches the message listener before any `await`, then flushes a queue after setup. This correctly handles the race where the client sends Sync Step 1 before the server finishes loading MongoDB/Redis state.

6. **Multi-instance ready** — Redis Pub/Sub bridges doc updates, awareness, permission changes, room-deleted events, and SSE notifications across server instances.

7. **Dual-layer role enforcement** — Viewer read-only is enforced at the WebSocket protocol level in `docSync.js` AND in the client UI. A viewer cannot edit even by bypassing the UI.

8. **Well-structured code** — Clear separation: routes → controllers → services → models. WS logic is split across focused files. Functions are small and named clearly.

9. **Bundle splitting** — `vite.config.js` chunks Monaco, Yjs, and React into separate bundles so Monaco is not downloaded on the login page.

10. **Full CI/CD pipeline** — Three-job CI (lint + tests + bundle budget → Docker smoke test → security audit) followed by GHCR push → Render deploy → readyz polling → production smoke test.

## 13. WEAKNESSES & LIMITATIONS

### Security

1. **JWT stored in `localStorage`** (`lib/api.js` line 22, `hooks/useAuth.js` lines 7–8) — Accessible to any JavaScript on the page. If there is ever an XSS vulnerability, the token can be stolen. `httpOnly` cookies would be safer.

2. **CSP disabled** (`app.js` line 22: `contentSecurityPolicy: false`) — Removes a key XSS defence. It was disabled to allow flexibility with the Vercel frontend, but a proper CSP policy should be added.

3. **In-memory rate limiter not shared across instances** (`middleware/security.js`) — An attacker on a multi-instance deployment can split requests across instances and bypass the per-IP limit. A Redis-backed rate limiter would be correct.

4. **Forgot password is a dead end** (`pages/auth/ForgotPasswordPage.jsx`) — The page is rendered and linked from the login screen, but there is no backend endpoint. Users cannot recover their account.

5. **No email verification** — Users can sign up with any email address they don't own.

6. **Password has no complexity requirement** — Only a minimum length of 8 characters is enforced server-side.

### Testing

7. **Only 3 unit tests** (`server/tests/unit.test.js`) — No tests for auth controller, rooms controller, invite controller, any middleware, or any frontend component.

8. **No integration tests** — No tests that actually start the Express server and make HTTP requests against it.

9. **Playwright is installed but unused** — `playwright` is in `client/devDependencies` but there are no e2e test files anywhere in the repo.

### Error Handling

10. **No current-password check in `updateMe`** (`auth.controller.js` → `updateMe()`) — Any valid JWT holder can change their own password without knowing the current one.

11. **SSE error handler is a no-op** (`hooks/useUserEvents.js` line 51: `es.onerror = () => {}`) — Errors are silently swallowed with no logging.

### Scalability

12. **In-memory Y.Doc registry per instance** (`docStore/docRegistry.js`) — Memory scales linearly with active rooms per instance. Very large deployments would need an external Y.Doc store.

13. **No pagination on room or member lists** (`rooms.controller.js` → `listRooms()` does `Room.find(...)` with no limit) — A user in thousands of rooms would get a very large response.

### Code Quality

14. **Hardcoded rate-limit defaults are very high** (`app.js` line 72: `10000 req/min` global, line 76: `2000 ticket req/min`) — Effectively disabled in practice.

15. **Room deletion reuses `room-deleted` event for member removal** (`rooms.controller.js` line 239) — The removed user sees a "room was deleted" toast instead of a "you were removed" message, which is confusing UX.

## 15. TOP 5 TECHNICALLY INTERESTING PARTS

### 1. Early Message Queue in WS Connection
**File:** `server/src/ws/connection.js`

`ws.on('message', ...)` is attached BEFORE any `await`. Messages arriving during async setup (MongoDB role load, Redis INCR, snapshot load) are buffered in `messageQueue[]`. After setup completes, the queue is flushed in order before marking `setupDone = true`.

This solves a subtle race condition: `y-websocket` sends Sync Step 1 immediately after the TCP handshake, but the server needs time to query MongoDB and load the Yjs snapshot. Without the queue, the first client message would be silently dropped, the editor would show "CRDT SYNCING…" forever.

### 2. REMOTE_ORIGIN Sentinel to Prevent Redis Loops
**File:** `server/src/ws/docSync.js` line 15 and `redisBridge.js` line 63

```js
const REMOTE_ORIGIN = Symbol('redis-remote-doc-update')
```

When a Yjs update arrives from Redis, it is applied with this Symbol as the `origin`. The `ensureUpdateBroadcast` listener checks `if (origin !== REMOTE_ORIGIN)` before calling `publishDocUpdate()`. This one-line guard prevents an infinite Redis loop: Server A publishes → Server B receives and applies → fires 'update' → Server B publishes back → Server A receives… and so on.

### 3. Atomic Invite Redemption with $expr
**File:** `server/src/controllers/invites.controller.js` lines 73–88

```js
Invite.findOneAndUpdate(
  { _id, expiresAt: { $gt: now }, $expr: { $lt: ['$usesSoFar', '$maxUses'] } },
  { $inc: { usesSoFar: 1 } },
  { new: true }
)
```

The `$expr: { $lt: ['$usesSoFar', '$maxUses'] }` condition compares two fields within the same document inside the atomic update. This is the correct way to prevent two simultaneous final-use redemptions from both succeeding. A naive read-then-write pattern would have a TOCTOU race condition.

### 4. Stateless Reusable HMAC WS Ticket
**File:** `server/src/services/ticket.service.js`

A custom JWT-style token signed with HMAC-SHA256. The key design decision is that it is **reusable** (not single-use). The comment explains why: `y-websocket` auto-reconnects with the same URL, and React StrictMode double-invokes effects — both cause a second WebSocket open with the same ticket. Single-use Redis tokens (GETDEL) would cause the second connection to get a 4001 error and trigger an unnecessary ticket refresh loop. The 10-minute TTL limits the window if a ticket is leaked. Role is NOT embedded — always looked up live so mid-session role changes take effect immediately.

### 5. Debounced + Force-Flush Snapshot Strategy
**File:** `server/src/services/snapshot.service.js` lines 30–47

The snapshot service has two flush triggers:
- **Debounce**: wait 3 seconds (`snapshotDebounceMs`) of no new updates before saving to MongoDB.
- **Force flush**: if 50 (`snapshotMaxUpdatesBeforeFlush`) updates accumulate without a quiet period (a fast typist, a paste), flush immediately.

This dual strategy means: a user typing continuously never waits more than 50 keystrokes to have their work persisted, but a brief edit followed by idle time waits 3 seconds (reducing MongoDB write frequency). This is a standard leaky-bucket + timeout pattern applied to database writes.
